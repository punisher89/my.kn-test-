# Telegram из d2o → Keenetic Pilot: аудит источников и безопасная заготовка

Изучен [t0fox/d2o](https://github.com/t0fox/d2o), его
`telegram/src/main.c`, `telegram/src/dc_map_store.c`,
`telegram/src/mtproto_probe.c`, `telegram/src/route_dns.c`,
`telegram/src/cf_domains.c`, `telegram/src/config.c`,
`telegram/src/route_plan.c` и
[инструкция Worker](https://github.com/t0fox/d2o/blob/main/telegram/cloudflare/README.md).
Идеи заимствуются с указанием источника, сетевой C-код d2o в Pilot не
перенесён. README d2o сообщает лицензию MIT; перед фактическим переносом
реализации сохранять авторские уведомления и проверить лицензии всех зависимостей.

## Какие серверы и данные использует оригинал

| Данные/соединения | Источник d2o | Что делаем в Pilot |
| --- | --- | --- |
| Начальный список DC Telegram | Статические известные адреса + собственный bootstrap | В будущей реализации: проверять встроенные адреса; не грузить произвольные IP из внешних списков |
| Актуальные DC и порты 443/5222 | Протокол MTProto `help.getConfig` через Telegram или подтверждённый WSS-маршрут; локальный LKG-кэш | Открывать перенаправление только после проверки IP/DC/порта и срока годности карты |
| Cloudflare WSS | Пул доменов получает по HTTPS с GitHub `Flowseal/tg-ws-proxy/main/.github/cfproxy-domains.txt`, хранит локальный кэш/запасной набор и поддерживает пользовательские Cloudflare Workers | **Чужой пул по умолчанию не использовать**; только свой hostname Worker |
| DNS | Системный resolver, Cloudflare, Google, dns.sb и внешний `d.webshiftvpn.ru` (встроенная таблица в `telegram/src/route_dns.c`) | Не перенимать адрес `d.webshiftvpn.ru` или скрытые внешние DNS; использовать штатный resolver и TLS-проверку своего Worker |
| MTProto/WebSocket мост | Локальный процесс `d2ktg` на C11; Cloudflare Worker пересылает данные дальше | Будущий **отдельный** процесс, с ограниченными памятью/CPU/FD и отключением по умолчанию |
| Внешние секреты/аккаунты | Для собственного Worker нужен Cloudflare-аккаунт и развёрнутый Worker; на 5222 свой список разрешённых IP; Telegram API ключи от пользователя не нужны | Никогда не спрашивать токен Cloudflare, сессионные ключи Telegram или приватную переписку |

Сама WebSocket-обёртка **не равна работающему Telegram**. HTTP 101,
TCP connect и успешный TLS не являются доказательством MTProto: нужно
подтверждение начального MTProto-обмена/ответа приложения. В d2o используются
проверки `resPQ`/конфигурации. На Keenetic Pilot эта проверка и локальный
прокси ещё не реализованы.

## Что реализовано в текущей тестовой ветке Pilot

- В «Сервисы и домены» появился блок
  **«Telegram · собственный WSS Worker (заготовка)»**.
- Можно задать только hostname собственного Worker, например
  `my-telegram.example.workers.dev`, без схемы/пути/порта/пароля.
  Настройка хранится в `/opt/etc/keenetic-pilot/telegram-relay-draft.json`,
  без включения внешнего доступа.
- Сохранение выполняется через защищённые
  `GET /api/telegram/relay-draft` / `PUT /api/telegram/relay-draft`.
  Формат запроса: `{"worker_host":"my-telegram.example.workers.dev"}`.
  Пустое значение очищает настройку.
- **Нет** автоматической загрузки списка от автора d2o, обхода через CF,
  службы-прокси, iptables REDIRECT, слушающего порта, дополнительного TLS
  соединения или проверки Worker.
- Существующий `telegram_mtproto` в nfqws2 — независимая
  экспериментальная подмена MTProto TCP, и она продолжит работать как раньше.
  YouTube, PPE, QUIC, очереди и оба канала обновления остаются без изменений.

## Как самостоятельно подготовить свою сторону Cloudflare

1. Создать Cloudflare Worker в своём аккаунте.
2. Взять **проверенную собственную копию** шаблона
   [d2o/telegram/cloudflare/worker.js](https://github.com/t0fox/d2o/blob/main/telegram/cloudflare/worker.js)
   и изучить его доступы. Установить в Cloudflare через редактор Workers.
3. Если требуется 5222, заполнять `D2O_TG_5222_TARGETS` **только**
   проверенными Telegram DC endpoint-адресами этого порта, а не любыми IP
   из интернета. Без подтверждённой карты оставить 5222 выключенным.
4. Записать hostname своего `workers.dev` в блок Pilot. Это подготовит
   конфигурацию для будущего sidecar, но пока **не изменит Telegram**.
5. После отдельного, тестируемого переноса sidecar в Pilot план:
   проверка подписи/версии бинарника, изоляция ресурсов, ограниченные
   connection limits и буферы, автономная проверка DC, исключение рекурсивного
   NFQUEUE, атомарный rollback и только затем явное включение proxy.

Сторонние Cloudflare-прокси несут риски конфиденциальности и доступности.
Не объявлять работу всех сообщений/медиа и звонков подтверждённой без
полевых измерений на роутере. Существующие файлы d2o, ключи и бинарники
в рабочую систему Pilot не устанавливать автоматически.
