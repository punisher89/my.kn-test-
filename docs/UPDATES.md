# Обновление Pilot из меню

С `0.2.0-alpha.10` откройте **Обновления → Проверить версию → Установить**.
Чтобы получить само меню на старой версии, сначала один раз выполните прежнюю
установочную SSH-команду. Пункт обновляет Pilot, панель, Lua-контроллер и
закреплённый nfqws2 как согласованный пакет; это не обновление KeeneticOS.
Каталог подписанных стратегий можно загрузить отдельно той же страницей.

Меню установки работает для управляемой службы с маркером Pilot, штатными
путями относительно своего префикса, init-скриптом и PID-файлом текущего
контроллера. В `/opt` нужен root. Режим разработки показывает сведения о
версиях, но не запускает установку. Для локальных тестов поддерживается свой
префикс; системные пакеты и правила реального роутера в таких тестах не меняются.

Проверки и порядок:

1. Получить `packages/latest.json` и подпись, проверить отдельным Ed25519-ключом.
2. Предложить только более новый выпуск `X.Y.Z-alpha.N`. Установить можно только
   версию из проверенных сведений; произвольные URL и команды не принимаются.
3. Проверить SHA-256 манифеста и выбранного архива для своей архитектуры.
4. Распаковать в приватный каталог, запретив обход путей, ссылки и специальные
   файлы; ограничить размер и число файлов. Проверить PLATFORM, VERSION,
   закрепление движка и версию нового бинарника.
5. Проверить чтение текущей конфигурации новым бинарником.
6. Запустить отдельный процесс установщика. Он проверит внутренний манифест,
   подготовит закреплённый движок, проверит nfqws2/Lua до остановки
   действующей службы. При ошибке применения сработает прежний откат установщика.
7. Проверить версию установленного бинарника и записать итог операции.

Установщик сохраняет настройки, пароль, ключи, списки, обучение, отчёты и
резервную копию предыдущего приложения. Он перезапускает службу, поэтому
соединения могут прерваться. Сеансы панели хранятся в памяти: после перезапуска
войдите снова с прежним паролем. Статус обновления переживает рестарт.

До остановки контроллера прочие изменения защищены блокировкой операций.
С alpha.16 чтение подписанных сведений о выпуске не использует эту общую
блокировку: проверка версии доступна во время подбора. Одновременные
проверки защищены отдельным признаком `checking`. При запросе установки
активный подбор получает отмену, новые фоновые задачи уступают место
обновлению, а подготовка пакета ждёт штатного освобождения блокировки
до 30 секунд. Этап `waiting` показан в панели. Если другая операция
не завершилась, установка не начинается, причина сохраняется в журнале.
Повторная установка не допускается, пока запрос ожидает или выполняется.
Процесс обновления отделён от контроллера и не завершается вместе с ним.
Неопознанный или погибший worker показывается как прерванное обновление.
Подробный журнал хранится локально рядом с config.json в `update.log`;
он не включается автоматически в диагностическую выгрузку. Не отключайте
питание при установке. При прерванной операции проверьте состояние службы и
резервную копию; отказоустойчивость при обесточивании не заявляется.

Проверки в среде разработки покрывают подписи, суммы, опасные архивы, отдельный
worker, сохранение конфигурации/пароля и завершение старого контроллера без
deadlock. Жизненный цикл настоящего установщика проверяется в отдельном
каталоге. Это не испытание обновления на KN-1811; его нужно подтвердить на устройстве.

API под обычной авторизацией и Origin: `GET /api/updates`,
`POST /api/updates/check`, `POST /api/updates/install` с полем `version`.

С alpha.15 установщик сравнивает установленный nfqws2, Lua, VERSION и ORIGIN
с пофайловыми SHA-256 из нового проверенного пакета. Эти хеши выводятся
`scripts/engine-file-pins.py` из архива, проверенного по `ENGINE_SHA256`;
полный локальный прогон сверяет их для всех пяти архитектур. Собственный
манифест установленного движка не служит основанием доверия. Подходящая
копия переносится в staging и проверяется повторно; при несовпадении
загружается закреплённый архив. Явно заданный `PILOT_ENGINE_ARCHIVE`
сохраняет приоритет и всегда проходит проверку исходного SHA-256.

После успешного запуска службы сохраняется только непосредственно предыдущая
версия приложения. Удаляются старые каталоги `keenetic-pilot.backup.*`
с собственным маркером Pilot; ссылки и неизвестные каталоги пропускаются.
При ошибке и `--no-start` автоматической очистки нет. Настройки и отчёты
в `/opt/etc/keenetic-pilot` и наблюдения в `/opt/keenetic-pilot-state`
не являются резервными копиями приложения и не очищаются.

Проверить место и удалить все старые копии вручную через SSH:

```sh
df -h /opt
du -sh /opt/keenetic-pilot.backup.*
rm -rf /opt/keenetic-pilot.backup.*
df -h /opt
```

Удаление всех копий убирает возможность вернуться к ним. При отказе обновления
смотрите `/opt/etc/keenetic-pilot/update.log` и `update-status.json` в том же
каталоге. Подготовка пакета тоже записывается в журнал; `phase` и `exit_code`
позволяют различить этап и код завершения процесса без публикации текста
журнала в API. Завершение сигналом не объявляется успешным обновлением.

Метрики: `GET /api/device`. Linux thermal/hwmon отдаёт температуру
в миллиградусах; при отсутствии датчика значение не придумывается. С alpha.17
фиксированные команды `ndmc -c 'show interface WifiMaster0'` и `WifiMaster1`
добавляют температуру Wi-Fi из CLI Keenetic в градусах. Требуются совпадающие
id и type WifiMaster, числовая температура в допустимом диапазоне. Не более
16 КиБ вывода и двух секунд на команду; общий кеш — 30 секунд. Прочий вывод
интерфейса не сохраняется и не экспортируется. Процент CPU
и скорость WAN требуют двух последовательных замеров; обнуление счётчиков
или смена интерфейса сбрасывают вычисление скорости. Load average — отдельная
метрика очереди задач, а не процент CPU. Недоступные данные возвращаются null.

## Контроль нагрузки

С alpha.19 порог защиты снижен с 85%/1,5 нагрузки до 65%/1,0 нагрузки для двухъядерных роутеров. Фоновый доменный подбор теперь проверяет ресурсы **до чтения накопленной истории и запуска HTTPS-проб**. Текущий движок и правила обхода при этом не останавливаются. Ручные проверки остаются доступны.\n\nС alpha.11 защита включена по умолчанию, в том числе при чтении старой
конфигурации. Перед началом фоновых задач и между сервисами контроллер
проверяет доступную память, CPU и load average. Новые фоновые загрузки
каталогов/доменов, проверки и запуск подбора откладываются при CPU ≥65%,
load за минуту ≥1 × число ядер либо доступной памяти менее 16 МиБ / 8%.
Лёгкий замер CPU, памяти и load кешируется на две секунды, чтобы соседние
пробы не оценивали CPU по одному тику. Датчики Wi-Fi и WAN при этом не читаются.
Плановый цикл оценивает ресурсы каждые 30 секунд, доменная очередь — каждые
две секунды и между пробами. Уже начатая операция не прерывается
по показателю CPU; действующий движок не останавливается. Ручные операции
остаются доступны с прежней блокировкой. Неизвестные метрики не считаются
измеренным нулём; защита использует доступные показатели. Температура здесь
информационная: у разных чипов разные допустимые пределы.

Помимо прежней паузы и лимита домена/контекста вводится общий бюджет всех
коробок: по умолчанию 30 смен метода за 10 минут, настраивается от 1 до 300.
Он ограничивает только новые смены после сбоев и сохраняет текущий метод;
выход из паузы требует новых подключений. Причина — «Лимит смен домена или
движка». Общий счётчик относится к одному процессу nfqws2 и сбрасывается
при его перезапуске; прежние индивидуальные счётчики доменов сохраняются.
Формат PILOT4 не изменён. Ограничение не является жёсткой квотой CPU/пакетов.

Коробки — группы наблюдений внутри общего движка. Отдельных достоверных CPU
и RAM для каждой коробки нет. Панель показывает общий CPU/RAM роутера,
состояния доменов и сумму записанных смен в ещё действующих индивидуальных
10-минутных окнах. Это не счётчик использованного общего бюджета процесса.
Проблемные свежие коробки отображаются первыми, старая история свёрнута.

Датчики Wi-Fi читаются из hwmon и ieee80211 с именем драйвера/канала; совпавшие
пути одного датчика объединяются. Непредоставленные драйвером температуры
не подменяются температурой CPU. Поддержка этих интерфейсов проверена
локально на файлах-образцах; фактическая доступность зависит от KeeneticOS.


## Дополнительные обновления ChatGPT / Codex из панели (alpha.20)

Исходный Ed25519-подписанный канал `packages` остаётся без изменений.
На странице «Обновления» дополнительно появились два независимых источника:
**ChatGPT** и **Codex**. Кнопка «Проверить» каждого источника получает
`ssh-releases/latest-chatgpt.json` или `latest-codex.json` и сравнивает
с неизменяемым `v<VERSION>/release-info.json`. Указатель проверяется
строго из известного репозитория GitHub, недопустимые источники отклоняются.

**Доверие отличается от официального канала:** источник ChatGPT/Codex
использует HTTPS к GitHub и контрольные суммы SHA-256 самого манифеста и
архивов, а не независимую подпись Ed25519. Метка ChatGPT/Codex — поле
выпуска, а не криптографическое доказательство автора. Без подтверждения
пользователя новый канал не запускает установку и не изменяет настройки.
Если GitHub или право публикации в ветку окажутся скомпрометированы,
SHA-256 из того же репозитория не заменит независимую подпись.

Установка через страницу использует отдельные защищённые API
`GET /api/updates/sources`, `POST /api/updates/sources/check`,
`POST /api/updates/sources/install`. Все наследуют аутентификацию
и проверку Origin существующего API. Перед остановкой Pilot новый
источник проверяет SHA-256 манифеста и архива подходящей архитектуры,
зафиксированный nfqws2, платформу, версию бинарника и совместимость
с текущей конфигурацией. Используются штатные исключительный lock,
отмена активного поиска, staging, detached worker и прежний установщик
с `--skip-packages` (никаких обновлений opkg). Пакеты ниже установленной
версии и не проверенные в этой сессии не устанавливаются. При ошибке
работающая служба остаётся прежней либо штатно откатывается.

Для перехода со старой alpha.19 потребуется **одно** SSH-обновление
до alpha.20, после чего новые выпуски ChatGPT/Codex можно получать
через страницу. Никаких приватных ключей на Windows не требуется.
